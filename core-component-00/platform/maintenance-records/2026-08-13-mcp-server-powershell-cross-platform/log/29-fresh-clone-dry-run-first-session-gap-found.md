| **Outcome**               | Confirmed defect, not previously isolated by this topic: on a genuinely fresh clone on any OS whose interpreter suffix does not match `.mcp.json.example`'s hardcoded default (currently Windows) — i.e. every first Linux/macOS/WSL clone — the fully-automated `SessionStart` hook chain (`mcp-config-platform-check.py` then `mcp-venv-bootstrap.py`, run exactly once, no manual step) leaves `.mcp.json` pointing at a non-existent interpreter path for the entire first session, even though both hooks report success and `mcp-venv-bootstrap.py`'s own message says "Reconnect the affected server(s) (e.g. `/mcp`) to pick this up." That instruction does not actually work: a manual `/mcp` reconnect re-reads the same stale `.mcp.json` — nothing in the automated chain rewrites it after `uv sync` creates the venvs. The path only self-heals on a **second** `SessionStart` (i.e., restarting Claude Code), because `mcp-config-platform-check.py`'s self-heal branch only runs at `SessionStart`, not on a manual `/mcp` reconnect. This exact mechanism is why Item #8's closure (`log/20`–`log/21`) read clean: `log/20` step 6 manually re-ran `mcp-config-platform-check.py` out-of-band before the CEO's `/mcp reconnect`, which is not something a real first-time user does or is told to do anywhere in the hook's own messaging. Both `uv sync` calls, the venv contents, and both servers' actual runtime behavior (once correctly addressed) are all confirmed sound — this is specifically a same-session config self-heal ordering gap, not a venv-bootstrap or server defect. Not closing Items #8/#9/#10 or reopening them (their own specific scopes — venv creation, degraded search, FAISS directory — are each still correctly fixed); this is a new, narrower residual gap in the same bootstrap chain, opened as Item #11 below. |
