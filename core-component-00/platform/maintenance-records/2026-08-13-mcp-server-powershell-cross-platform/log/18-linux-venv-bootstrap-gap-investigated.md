| **Outcome**               | The hook exists, is correctly wired, and is functioning exactly as designed — it is not the "gap" the CEO's framing implied. The actual root cause is that this specific machine has never had either server's `.venv` bootstrapped (`uv sync` never run here), which is a scenario outside `mcp-config-platform-check.py`'s designed scope by its own docstring: "a server whose venv doesn't exist for either OS is left untouched... this hook fixes the one specific, previously-incident-causing failure mode (OS-mismatched venv path), nothing else." This is the same class of gap the topic's own Item #6 closing note (`log/17`) flagged as residual and untested: "whether Claude Code reads `.mcp.json` before or after `SessionStart` hooks on a genuinely empty first clone was never directly tested." The CEO then asked whether the existing hook should be extended to also run `uv sync`, or whether a new, independent hook should handle that. Recommendation given: keep them separate — the existing hook's entire safety contract (cheap, read-mostly, fail-open on every `SessionStart`) was built specifically because the CEO previously rejected an unconditional-rewrite design as too risky near an already-connected server (`log/14`); `uv sync` is a slow, mutating operation (package installs) that would break that contract if folded into the same hook. A separate hook, triggered only when this hook reports `neither_os_path_exists`, isolates the slow/mutating operation behind its own explicit trigger and matches how the rest of `.claude/hooks/` is already factored (one hook per concern). |
